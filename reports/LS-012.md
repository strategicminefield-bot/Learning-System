### 4. Why API DB auth fails

**READ FROM A RECORD** (pg_hba_file_rules):

```json
{
  "rule 2": "host all all 127.0.0.1/32 trust",
  "rule 3": "host all all ::1/128 trust",
  "rule 7": "host all all all scram-sha-256"
}
```

**READ FROM A RECORD** (postgres listen_addresses): `*`

**OBSERVED NOW:**

| How connection is made | Works? | Why |
|---|---|---|
| `docker exec postgres psql -U fabric -d learning_fabric` | ✅ Yes | Unix socket → `local all all trust` rule |
| `psql -U fabric -h localhost -d learning_fabric` | ✅ Yes | TCP to 127.0.0.1 → `host all 127.0.0.1/32 trust` rule |
| `psql -U fabric -h postgres -d learning_fabric` with PGPASSWORD=fabric | ❌ No | TCP to Docker bridge IP → `host all all all scram-sha-256` rule → password mismatch |
| `psycopg.connect(DATABASE_URL)` from API container | ❌ No | Same — connects to `postgres:5432` (Docker bridge) → SCRAM-SHA-256 required |

**Root cause:** The API container connects to `postgres:5432` which resolves to the Docker bridge IP (172.19.0.x), NOT to 127.0.0.1. The pg_hba.conf at that IP range requires **SCRAM-SHA-256 password authentication**. The password in `DATABASE_URL` does not match the password stored in PostgreSQL's `pg_roles` for the `fabric` user.

**Why the mismatch exists:** The `fabric` role's password was set when the postgres container was **first created** with a POSTGRES_PASSWORD value from the `.env` file at that time. The `.env` file may have been updated since, or the API container was created/recreated with a different `.env` value, but the postgres container retains the original user credentials from its first bootstrap.

**API container logs confirm:**

```
psycopg.OperationalError: connection failed: FATAL:  password authentication failed for user "fabric"
```

### 5. Whether fixing DB auth would make the migration endpoint capable of executing SQL

**INFERRED:** Yes. Once the password in `DATABASE_URL` matches PostgreSQL's stored password for the `fabric` role, the migration endpoint at `POST /api/v1/migrations/apply/{n}` would become **fully operational** — capable of executing arbitrary caller-supplied SQL against the production database with **no authentication, authorization, or input validation**.
